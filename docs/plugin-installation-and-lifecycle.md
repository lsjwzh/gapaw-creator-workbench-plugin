# 插件安装、刷新识别与首次启动

日期：2026-10-23。状态：宿主源码核查、接入方案与可点击模拟原型。尚未实现真实安装包、宿主安装接口或持久生命周期管理。

## 1. 用户入口

达人工作台以独立插件目录交给 MultiCC 管理。用户有两种入口，最终进入同一套校验和初始化流程：

- **主动安装**：在 MultiCC 的插件管理页点“安装插件”，选择完整的本地发行包；宿主检查内容和兼容性，安装到实际插件目录，再识别和加载入口。
- **手动复制**：用户把完整插件目录放进管理页显示的插件根目录，然后点“刷新识别”；宿主重新扫描，显示新插件、错误和配置状态，通过校验后加载入口。

首次加载达人插件时，必须引导设置持久的专属工作目录。完成后即可套用回本率提示词发送任务。Chrome 环境与平台连接可以后补；需要读取平台时再检查具体能力。插件初始化、刷新和启动均不自动发送选人任务。

目标流程：

```text
主动安装 ── 校验发行包、完整落位 ─┐
                               ├─ 发现与校验 ─ 加载入口 ─ 首次设置专属目录 ─ 工作台就绪
手动复制 ── 点击刷新识别 ────────┘                         │
                                          已配置实例恢复原绑定
```

界面由宿主负责“安装插件”“打开插件目录”“刷新识别”和插件状态卡片；达人插件负责专属目录初始化、回本率提示词、任务关联和业务结果。安装入口不能藏在尚未安装的插件里面。

## 2. 已有能力与待补能力

以下为当前源码核查结果，不是对未来实现的承诺。

| 能力 | 当前实际行为 | 本次方案 |
| --- | --- | --- |
| 插件根目录 | 运行中的 MultiCC 代码根目录下的 `plugins/` | 页面显示宿主实际解析的绝对路径，不能把开发工作区路径写死 |
| 目录发现 | `GET /api/plugins` 每次扫描目录 | 复用扫描入口，返回成功项与失败项，补充初始化状态 |
| 刷新 | 插件面板工具栏“刷新”会清缓存并请求清单 | 保留这个入口，明确为“刷新识别”，展示本次发现及失败数量 |
| 重新打开管理面板 | 清单可能仍来自内存缓存；全局页头刷新也不保证重新扫描 | 明确区分重绘与重新扫描；安装后主动触发同一刷新流程 |
| 主动安装 | 没有安装按钮或安装接口 | 增加本地发行包安装；网络地址安装与市场分发不纳入首期 |
| 初始化和激活 | 没有宿主生命周期模型 | 加载后读取持久绑定，进入待初始化或就绪状态；失败可见、可重试 |
| 命令执行 | `command` 引擎在每次调用时启动进程，完成后退出 | 首期沿用按需命令，不为了“已启动”常驻一个空进程 |
| 错误清单 | 损坏清单等被静默过滤；二进制存在并不证明可执行 | 显示失败卡片及具体修复动作，检查权限、平台和界面入口 |
| 刷新与升级 | 没有版本锁、原子替换、回滚和进程管理 | 刷新本身不覆盖版本、不重置配置、不停止正在使用的环境 |

宿主冷启动时应执行同一套发现与状态恢复；运行中手动复制后由用户点击刷新识别，不依赖文件监听。此冷启动恢复属于待补能力，当前仅有按请求扫描。

打包版 MultiCC 还须明确可写且不会随应用升级被替换的插件安装根目录。当前源码中的代码根目录方案不能直接当作打包版持久安装契约；“打开插件目录”和安装器必须读取同一宿主配置。

## 3. “识别并启动”的状态含义

| 状态 | 进入条件 | 页面操作 |
| --- | --- | --- |
| 未发现 | 当前扫描结果中不存在有效安装目录 | 安装插件、打开插件目录、刷新识别 |
| 校验中 | 已发现候选目录，检查完整性与兼容性 | 显示进度，重复刷新合并执行 |
| 校验失败 | 清单、入口、平台产物、权限或版本不满足要求 | 显示插件目录与原因；修复后重新检测 |
| 加载中 | 校验通过，读取配置并加载插件入口 | 显示进度，不提前标记为就绪 |
| 待初始化 | 插件入口可用，尚未绑定有效的专属工作目录 | 进入设置向导；暂不能创建新任务 |
| 就绪 | 插件入口可用，专属目录绑定有效且已读回 | 打开工作台，编辑提示词并发送任务 |
| 加载失败 | 配置读取、入口加载或必要的初始化命令失败 | 保留配置，显示失败阶段，允许重试 |
| 待修复 | 曾配置的目录失效或配置不兼容 | 修复目录绑定；保留历史任务关联 |

这里的“就绪”表示可以使用工作台并发起任务；不表示已登录 TikTok Affiliate、Kalodata 或已开始采集。连接卡片独立显示“未配置、待登录、可读取、权限不足”等实际状态。出口正常、自动化可控制浏览器、平台可读取数据是三项不同的检测结果。

首期使用宿主现有的按需命令模型，启动指加载入口与恢复配置，没有应当常驻的工作台服务。每次业务命令是否执行成功仍需独立回执。如后续确实需要常驻服务，另行扩展启动、健康检查、停止、崩溃恢复与升级协议，不能让现有 `available` 字段同时表示这些含义。

Chrome 出口插件自己管理浏览器和监督进程。安装或刷新达人插件不启动 Chrome、不停止已有浏览器、不切换账号，也不把它的私有控制管道当成已经可用的自动化接口。

## 4. 安装与刷新行为

### 4.1 主动安装

首期建议接收本地发行压缩包，格式与兼容声明须随实际宿主实现确定；当前没有可用的压缩包安装 API。

1. 选择文件后读取清单，展示名称、版本、来源说明、目标目录和首次安装／升级类型。
2. 在宿主临时准备区展开并校验：清单版本、目录名与插件编号一致、引擎和命令白名单、平台产物、执行权限、界面入口、文件边界。不允许绝对路径、目录穿越或指向安装目录外的链接进入目标；不执行包内任意安装脚本。
3. 按插件编号串行化安装，检查正在执行的命令及版本占用。无法安全替换时保持当前版本并提示等待；不直接覆盖正在使用的目录。
4. 所有检查完成后，在同一文件系统完整切换到目标目录。保存安装记录与可恢复的旧版引用；失败回滚，不留下可被误识别为完整插件的半成品。
5. 调用与“刷新识别”相同的发现、加载和初始化流程。界面分别显示安装完成、待初始化或加载失败；安装成功不能吞掉后续加载错误。

主动安装是否允许读取选定本地文件与写入插件根目录，由宿主的安装操作承担。加载不顺带读取真实业务库、迁移旧资料或执行平台任务。

### 4.2 手动复制后刷新

用户复制完整的 `plugins/<插件编号>/` 后点击“刷新识别”。发现新目录则校验并加载；已配置同版本实例恢复原绑定；内容不完整或不兼容则留在错误卡片中，不能从清单中消失。首次发现时进入专属目录向导。

对已安装版本的手动覆盖不能保证原子性。宿主应检测文件变化，将新命令执行置于待校验状态，已有执行不强制中断；校验通过后才恢复调用。若没有可恢复旧版，不宣称可以自动回滚，提示重新放入完整发行包。升级优先走主动安装流程。

重复点击刷新只合并或重做只读检查，不能重复创建专属目录、注册任务、投递消息或清空操作记录。同一插件、版本与配置的初始化应幂等；版本改变仅运行声明并验证过的配置升级步骤。

若安装目录已被移除，卡片应显示安装缺失并保留持久配置关联，不再启动新命令；历史任务仍可从原 MultiCC 任务访问。卸载默认只移除程序与激活登记，不删除运营专属目录、历史会话或浏览器登录目录。

### 4.3 页面刷新与状态恢复

“刷新识别”是宿主重新扫描；浏览器整页刷新是重新加载前端。正式实现两者都从持久记录恢复插件绑定和任务状态，不能依赖 iframe 内存。扫描失败要保留已有状态并标记过期，不得误判为所有插件已被卸载。

当前原型用内存模拟：原型里的“刷新识别”和页面间切换保留数据；真正刷新整个浏览器页面会清空演示。它不证明持久恢复已经实现。

## 5. 四类目录与记录归属

| 位置 | 内容 | 升级、刷新后的要求 |
| --- | --- | --- |
| 插件安装目录 | 清单、平台二进制、界面和随包方法模板 | 可以整体更新；不保存用户业务数据、密钥或登录态 |
| 宿主持久配置区 | 插件登记、启用状态、安装版本、专属目录绑定及配置版本 | 读回恢复；按宿主用户／实例及插件编号隔离，不写入代码目录 |
| 用户专属运营目录 | 运营项目归属、批准的方法资料、业务结果；任务关联由宿主保存 | 初始化由用户选定，卸载和升级不删除，不采用回收型任务工作区 |
| Chrome 登录目录 | 隔离身份、浏览器登录状态 | 继续归出口插件管理，达人插件只保存环境引用 |

完整会话仍保存在 MultiCC；专属目录用于承载项目与后续对话归属，不另复制聊天历史。切换默认专属目录只影响新任务，不能修改旧宿主目录记录的路径来搬走历史任务。

## 6. 交付边界与实现顺序

宿主和达人插件分开交付：

- **MultiCC 宿主**：安装入口、插件目录选择／展示、发现结果、兼容校验、持久登记与生命周期读模型。新增核心用 Rust 异步实现，现有 Node 路由仅保留必要适配，在 MultiCC 独立工作区开发。
- **达人插件**：发行清单、平台产物、中文界面、读取／保存配置的命令、专属目录向导、回本率提示词与两阶段任务投递。插件代码在本仓库开发。
- **Chrome 出口插件**：继续拥有环境与出口启停；受控自动化桥接另行接入，不将管理权限复制到达人插件。

现有 `schema:1`、`command` 引擎没有初始化钩子、兼容范围和健康协议。任何新增清单字段、状态接口或初始化命令都须先明确宿主支持，不能仅加字段就宣称安装可用。本轮不放置假的 `plugin.json`、空二进制或伪成功接口。

先交付宿主安装与刷新状态契约，再交付插件完整发行包和目录初始化，之后接任务投递、环境桥接及结果回写。端到端验收至少覆盖：首次主动安装、手动复制刷新、错误包显示、重复刷新无副作用、重启恢复绑定、加载失败重试、升级失败保留旧版、旧任务继续原目录。
